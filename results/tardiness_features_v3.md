# Does absolute lateness information help the tardiness specialist? Benchmark v3

Protocol: `docs/tardiness_features_protocol_v3.md`. Generated by `tools/analyze_tardiness_features_v3.py`. Single training seed (111): numbers only, no significance claims. Evaluation split only; the reserved final-test sets were never loaded.

## The change

**"Tardiness specialist, with lateness inputs"** is the committed tardiness specialist's training run ("Tardiness specialist, current", DANIEL-T s111) with one option on, `--lateness_inputs on`. It adds five per-job features to every operation's input, all in fixed units (time / 99, the benchmark's time scale) and not rescaled per step:
- current time;
- due date − current time, signed (negative means overdue);
- absolute slack (due date − earliest start − remaining minimum work);
- an already-late flag;
- a will-be-late flag.

**Where they enter the network.** The operation features feed the first operation-attention layer and the edge input of the first machine-attention layer. Those 8 weight matrices grow from 12 × 32 to 17 × 32 (+1,280 parameters, 29,602 → 30,882), and nothing else changes. The 12 existing features are unchanged and still rescaled per step.

**With the option off,** a 5-update run gives bit-identical weights and validation values before and after the change.

**Two differences from the committed run** are unavoidable or outside the run:
- The first-layer shape differs, so every layer's random initialisation differs. The training-instance stream is the same.
- The committed run shared the PC with CP-SAT, on separate CPUs, so wall-clock is comparable only approximately.

## Consequence for merging and distillation

The new specialist's operation input has 17 features against the current specialists' 12. Its first attention layers therefore have 17 × 32 weight matrices where the makespan and carbon specialists have 12 × 32. It cannot be weight-averaged, task-arithmetic-merged or TIES-merged with them, and the merge-then-fine-tune and distillation pipelines (which load every source with the 12-feature schema) refuse it. If the change is adopted, one of the following is needed:

1. **Retrain the makespan and carbon specialists with `--lateness_inputs on`** (all sizes and seeds). Every specialist then shares the 17-feature schema. This is the clean option, but it means new specialists and new merges, and the MO network and its preference-conditioned schema would need the same option.
2. **Pad the current specialists.** Add five zero rows to their 8 first-layer matrices. A zero row makes a network ignore that input exactly, so their behaviour is unchanged, the same device the merges already use for the preference columns. They can then be merged with the new specialist. Their padded rows are zero rather than learned, so a merge dilutes the new specialist's use of the lateness inputs.
3. **For distillation only:** the student uses the 17-feature input, and each teacher receives the first 12 columns, which are unchanged. This needs the distillation code to slice the teachers' inputs; no retraining is required.
